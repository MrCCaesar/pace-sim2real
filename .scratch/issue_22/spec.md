# Issue #22 · 任务组织检查规格

状态：Approved。依据为 [R1–R12](requirements.md)、[Research](research.md) 和 [ADR 0020](../../adr/0020-task-organization-lint.md)。本规格、[接口](interfaces.md)和验收条件为 Plan 的基准。

## 职责和适用范围

Ruff 负责仓库 Python 源码与存根的通用 lint，沿用 pyproject.toml 已配置的规则。独立检查器静态读取被检查项目的源码、存根和项目元数据，检查任务目录以及配置引用的实际定义位置。任务代码、框架、仿真及 GPU 均无需加载。实现可共享一份模块索引，先记录定义和导出，再解析继承与配置绑定。对源码无法证明的结论单列报告。

| 规则 | 触发条件与判定 |
| --- | --- |
| ORG001 任务布局 | 以项目的任务注册入口、环境配置定义和任务注册记录发现任务，包括仍位于旧目录的任务。任务家族根为 `src/<项目包>/tasks/<任务>/`。以官方 v3.0.0 tag 为准，Direct 单智能体和多智能体家族分别由生成器加上 _direct 与 _marl_direct 后缀。所有项目采用同一目录约定。家族共享配置可以放在家族根；注册用的机器人变体配置放在 `config/<robot>/`，所属 agent 配置跟随变体。检查实际定义与注册目标。 |
| ORG002 地形 | 项目自定义的地形生成器、导入器、子地形配置子类，以及被地形配置的 `function` 绑定的本地生成实现，归入 `<项目包>_isaaclabs/terrains/`。仅组合官方地形配置、设置参数和实例化平面的场景配置允许就地定义。 |
| ORG003 Manager | 项目内直接或间接继承官方 ManagerBase 的 Manager 实现归入 `<项目包>_isaaclabs/managers/`。环境中的配置组保留在环境配置中；有状态的 ManagerTermBase 派生项依其绑定类别检查。只有实际存在扩展才要求相应包可导入。 |
| ORG004 MDP 项 | 根据配置类型及其 `func` 或 `class_type` 追踪本地实现。奖励、事件、观察、终止、课程分别归入任务的 `mdp/{rewards,events,observations,terminations,curriculums}.py`；动作、命令、记录项允许同职责的模块或子包。采用官方实现的类别无需空文件。直接式环境的官方方法按环境类契约识别；普通辅助函数仅在被绑定为项时检查。 |
| ORG005 引用未解析（失败行为已批准） | 对所有环境相关的组件绑定、注册入口、配置到实现的引用及判定归属所需的继承链，无法确定目标即失败。报告绑定文件、行列、原始引用和未解析原因，例如目标缺失、多个可能定义或运行时工厂。 |
| ORG006 环境、变体与注册 | 检查每个环境类、环境配置、场景组合、Gym 注册及其实际引用的配置和 agent 资源。按外部模板区分任务共享定义与机器人变体。Manager-based、Direct RL 和 Direct MARL 各按对应官方工作流判断；直接式环境的动作、观测、奖励、终止和重置等生命周期方法归环境类。 |
| ORG007 环境使用的框架扩展 | 可复用的自定义框架组件及其配套配置按官方同职责子目录归入扩展包。例如执行器与其配置归入 actuators/，传感器和控制器分别归入 sensors/ 和 controllers/。区分框架类型实现、任务专用组合配置和资源文件；例如机器人资源及配置可在外部模板的项目 assets/ 下，任务场景中可以实例化传感器。 |
| ORG008 缺少组织规则 | 已发现环境自定义组件、其绑定也已解析，但没有覆盖其职责及合法位置的规则时，报告定义、引用来源和缺少规则的类别，检查失败。为新类别补充同版本官方依据及正反样例后重新检查。 |

### 如何确定覆盖范围（R11）

范围由环境的组成关系和 Isaac Lab 扩展点决定。遍历每个任务的注册、环境与配置继承、配置组合、实现绑定、直接式环境构造的组件、变体和声明的资源入口；同时从项目源码反向发现环境类、扩展类型和任务注册，捕获错放在预期目录之外或尚未注册的定义。逐项区分项目自定义实现、任务内配置组合、上游复用和外部资源引用。归属证据包括框架基类、配置字段或构造调用、类型到实现的绑定和资源路径。普通标量参数及通用数学函数不单凭被调用而成为独立的环境扩展。

| 核对面 | 要追踪的内容 |
| --- | --- |
| 环境发现与工作流 | 包入口、任务注册、环境实现与配置、单智能体或多智能体、直接式或 manager-based、家族与变体、注册引用的训练配置及 Python/YAML 等资源。 |
| 环境装配与机器人 | 场景、机器人及其他资产、执行器、控制器、传感器、地形、生成和导入配置；从场景或机器人配置继续追踪嵌套的项目定义。 |
| 运行与交互 | 仿真配置、物理后端与自定义生成逻辑、噪声、延迟、设备与遥操作、渲染、可视化、窗口、标记和记录器等在环境中实际使用的扩展。 |
| 任务行为 | 全部 Manager、MDP 项与直接式生命周期，以及与这些行为绑定的项目函数、类和配置。共享组件可由多个任务引用同一定义。 |

上述各行是核对入口。每个已发现的环境组件须有可核查的分类结果；出现新类别走 ORG008，不能因没有专用规则而跳过。检查对象为代码组织和引用归属，资源引用核对其声明、来源及项目内路径；本规格不规定控制参数或机器人动力学数值。

支持显式和相对导入、别名、可静态确定的星号导出、存根重导出、项目内间接继承、字面量模块引用以及官方模板的模块相对引用。框架复用按可信的框架导入来源识别。缺少模块、循环或多个可能来源导致解析失败时适用 ORG005。动态工厂的返回值不得通过执行用户代码求值。

## 存量迁移与复用

PACE 任务家族采用 `src/pace_sim2real/tasks/pace/`。共享配置、MDP 和机器人变体迁移后，须同步更新包发现、Gym 注册字符串、公共导出、仓内直接导入、工具配置和使用文档。四个现有 Gym ID、对应配置、顶层公开导入和仿真参数须保持兼容。若有在仓外使用的旧深层导入路径，需在迁移前确认兼容要求。

建议在现有仓库提供独立 hook，调用者按固定 Git 修订复用。检查器从调用方项目读取包名，安装或调用该 hook 不应拉入 PACE 的运行依赖。该方式足以验证第二个项目的接入，暂时没有单独建仓的技术需求。通用 Ruff lint 与结构检查均纳入 agent 可调用的 pre-commit 入口；保留既有的其他适用检查，解决有效 hook 的配置错误后再做全库验收。

| 编号 | 要求 | 可观测结果 |
| --- | --- | --- |
| A1 · R5/R8 | 正确家族布局、现有旧布局、只有空 config 但实际变体仍在旧路径 | 正例通过，两个反例报 ORG001 并定位应迁移的配置。 |
| A2 · R5–R7 | 分别提供正确和错放的 Manager 间接子类、地形生成函数，另有使用官方地形和有状态奖励的配置 | 仅错放者报 ORG002/003；项目内函数的重导出不能掩盖原始位置。 |
| A3 · R5/R6/R9 | 同一任务只自定义奖励并复用官方事件；另将奖励移入配置文件，保留 rewards.py 的重导出 | 正例无需 events.py；别名、存根、静态字符串和传递重导出路径均能定位错放定义。 |
| A4 · R5 | 将已绑定的奖励改为运行时工厂，或删除被引用模块 | 报告未解析绑定和位置；退出状态依 ORG005。 |
| A5 · R2/R4/R10 | 通过另一个包名的最小外部项目调用同一固定版本 hook，再引入错放的奖励 | 无需安装 PACE 或启动 Isaac Lab；两次分别通过和失败，诊断引用调用方路径。 |
| A6 · R1–R4/R8 | 在清理后的完整仓库运行适用的 Ruff、结构及既有 hooks，加载各已注册任务配置，检查公共导入和现有回归测试 | 记录精确命令、退出码、检查范围及通过数；全库违规数为零；配置解析成功，物理参数和既有测试行为保持一致。 |
| A7 · R11 | 针对上表每个核对面和每条职责规则，准备一个官方允许的布局及一个错放或断链样例。使用 PACE 机器人配置追踪到 PaceDCMotorCfg 和 PaceDCMotor，并将同一资源由两个环境引用。 | 能定位执行器配置与实现，接受共享使用；区别任务配置与可复用实现。直接式、多智能体生命周期方法按对应工作流通过。 |
| A8 · R11/R12 | 新增未有专用规则的可解析环境组件；另对任务注册、资源和嵌套组件分别制造不可解析引用。 | 前者报 ORG008 并失败；后三者报 ORG005 并给出绑定位置及原因。涵盖全部环境的“通过”要求违规、未解析及缺少规则三项计数均为零。 |
